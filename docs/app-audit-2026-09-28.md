# Wasteless application audit — 2026-09-28

Scope: Flutter client, FastAPI API, applied Supabase schema/RLS, repository hygiene,
automated tests and web build artifacts. Branch audited: `codex/wasteless-mvp` at
`09cb6bb`.

## Remediation update

The pre-production pass after this audit implemented real password recovery,
single-instance per-token/per-user/IP rate limits, request timing logs, explicit
CORS, production API/web containers, SPA routing, compression/cache/security
headers, environment documentation and removal of the unused privileged backend
and Flutter demo stacks. Flutter analyzer is now clean.

The live-catalog and live-E2E findings remain open: `mar` and `para` still have
unknown stock, and no dedicated test inboxes were provided. The Supabase
organization is on the Free plan, so leaked-password protection cannot be enabled;
it remains a documented provider-plan limitation.

## Release decision

**Not ready for production release.** The authenticated commerce design is sound,
but the live catalogue contains no orderable products and the repository has no
production deployment configuration. Password recovery and a live end-to-end
purchase test are also missing.

## Findings

### P1 — Live catalogue has no orderable products

Both live products (`mar`, `para`) have `stock = NULL`. The `catalog_read` policy
only exposes products with non-negative stock, so authenticated users see an empty
catalogue. This correctly avoids inventing inventory, but blocks every purchase
flow until real stock is entered. Four legacy constraints remain `NOT VALID` to
preserve incomplete rows; they still protect new writes.

Action: enter verified inventory for each product, then validate the product
constraints after all legacy rows are corrected.

### P1 — No production deployment path is defined

The repository has no container, CI workflow or hosting configuration for the API
or Flutter web build. Configuration examples point to localhost. The build succeeds,
but there is no reproducible deployment, HTTPS API URL, environment validation in
CI, release rollback, or uptime check.

Action: select hosting, add a pinned production build/deploy pipeline, configure
HTTPS/CORS/secrets there, and add a post-deploy `/health` smoke check.

### P1 — Account recovery is absent

The live login hides the prototype's password-recovery control, and no
`resetPasswordForEmail` / password-update route exists. A user who forgets their
password cannot recover the account from Wasteless.

Action: implement the Supabase PKCE recovery flow, configure allowed redirect URLs
and production SMTP, and test both known and unknown email addresses without user
enumeration.

### P1 — No live end-to-end transaction has been verified

The database transaction is covered by isolated PostgreSQL tests, but signup,
session restoration, API authentication, cart, checkout and order history have not
been exercised together against the live project. Live stock is currently missing,
so this verification cannot complete.

Action: use two non-production accounts and real test inventory. Verify cross-user
isolation, refresh/restart behavior, idempotent retry and rollback after insufficient
stock.

### P2 — Leaked-password protection is disabled

The live Supabase security advisor reports `auth_leaked_password_protection`.
Supabase documents this protection as a Pro-plan feature. Review the plan and enable
it when available; otherwise enforce a strong minimum password policy and document
the residual risk.

### P2 — API abuse controls are incomplete

FastAPI verifies every bearer token and Supabase rate-limits Auth, but the commerce
API has no per-user request throttling. An authenticated client can repeatedly hit
catalog/cart/favorite endpoints and create avoidable Auth and PostgREST load.

Action: add gateway-level per-IP and per-user limits, with stricter limits on writes,
and retain the existing checkout idempotency key.

### P2 — Legacy code remains in production source trees

The active API only registers `commerce.py`, yet the repository still contains old
generic repositories, routes and services using a privileged Supabase client. They
are currently unreachable, and no secret value is tracked, but accidental future
registration could reintroduce broad reads or service-key usage. Flutter likewise
retains old prototype services/pages containing print calls and hard-coded local URLs.

Action: move prototype-only Flutter code under a clearly isolated preview package
and remove or archive the unused privileged backend stack after confirming no caller
depends on it.

### P2 — Web payload and runtime performance are unmeasured

The local release directory is 43 MB; `main.dart.js` is about 3.0 MB and CanvasKit
contains multi-megabyte WASM variants. Those are on-disk sizes, not transfer sizes.
No Chrome DevTools performance trace was available, and the repository has no
hosting cache/compression configuration, so Core Web Vitals cannot be reported
honestly.

Action: configure Brotli/gzip and immutable caching for hashed assets, then capture
mobile cold-load LCP/INP/CLS and request payloads on the deployed HTTPS origin.

### P3 — Database indexes need review once traffic exists

The performance advisor reports ten foreign keys without covering indexes, including
`order_items.product_id` and `product.location_id`. Four new indexes are reported as
unused, which is expected with zero orders and is not evidence they should be removed.

Action: retain the checkout/read-path indexes for now; add indexes only for measured
queries and revisit with `pg_stat_statements` after representative traffic.

### P3 — Static-analysis debt remains in legacy Flutter files

`flutter analyze` reports 13 informational findings: print calls, one async
`BuildContext` use, one file-name issue and deprecated color APIs. No analyzer errors
or warnings originate in the new commerce flow.

## Verified strengths

- Supabase is `ACTIVE_HEALTHY`; both migration versions are recorded remotely.
- Six commerce policies scope reads to the authenticated owner or valid catalogue
  rows. Anonymous table access and direct authenticated writes are denied.
- Privileged functions live in a private schema, use an empty `search_path`, verify
  `auth.uid()`, and are not executable by anonymous users.
- Checkout locks carts/products, derives prices server-side, snapshots order data,
  decrements stock, clears the cart atomically and uses a per-user idempotency key.
- No `.env`, local Flutter config, service-role value or JWT is tracked by Git.
- Current checks pass: 27 API tests, 31 database checks and 47 Flutter tests.
- The Flutter web release build succeeds. The analyzer has only the 13 informational
  legacy findings described above.

## Audit limitations

Chrome DevTools MCP was not configured, so no Core Web Vitals or network waterfall
was captured. Local preview/API processes were not running during this audit. No
production rows were modified, and no test accounts or fake stock were created.
